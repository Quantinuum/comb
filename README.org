#+AUTHOR: Selwyn Simsek
* Comb
A library to aid in the verification of the fault tolerant properties of state preparation circuits that use the CNOT + T gate set.

* Build
Comb depends on [[https://github.com/malb/m4ri][m4ri]]. The compatibility Makefile can build and install it into the =m4ri/= subdirectory. Ensure that autoconf, automake, Git, and Make are installed, then use the primary CMake and CTest build:
#+BEGIN_SRC shell
  make m4ri
  cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
  cmake --build build --parallel
  ctest --test-dir build --output-on-failure
#+END_SRC

On Apple Silicon with the dependencies installed through Homebrew, expose both
prefixes explicitly so CMake can find M4RI and =libomp=:
#+BEGIN_SRC shell
  brew install m4ri libomp
  cmake -S . -B build -DCMAKE_BUILD_TYPE=Release \
    -DCOMB_M4RI_ROOT="$(brew --prefix m4ri)" \
    -DCMAKE_PREFIX_PATH="$(brew --prefix m4ri);$(brew --prefix libomp)"
  cmake --build build --parallel
  OMP_NUM_THREADS=1 ctest --test-dir build --output-on-failure
#+END_SRC

The explicit single-thread setting is appropriate until the installed M4RI
library has been confirmed to be configured with thread-safe tables.

Verification circuit inputs are private data and are kept outside version control. Files ending in =.run= or =.run.gz= and the local =examples/= directory are ignored. Supply your own inputs through =COMB_EXAMPLES_DIR=/path/to/private/inputs make examples=, with =fault-tolerant/= and =non-fault-tolerant/= subdirectories. The benchmark extractor accepts the same environment variable or =--examples /path/to/private/inputs=. Synthetic test fixtures are generated by the test code when needed.

The rank, flat-layout, CUDA-stub, dense-tableau, sequential-reference, GPU-math, candidate-pipeline, and run-file tests can be built without M4RI by adding =-DCOMB_BUILD_CPU=OFF=. MPI scheduler tests with one, two, and three processes are included when MPI is available; their CUDA backend is mocked. A separate real-device differential test is built with =COMB_ENABLE_CUDA=ON=.

CUDA and MPI are opt-in. On the target Linux/A100 system use:
#+BEGIN_SRC shell
  cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo \
    -DCOMB_ENABLE_CUDA=ON -DCOMB_ENABLE_MPI=ON
  cmake --build build --parallel
  ctest --test-dir build --output-on-failure
#+END_SRC

The CUDA target defaults to native =sm_80= code, =compute_80= PTX, and line information. Override =CMAKE_CUDA_ARCHITECTURES= for another NVIDIA architecture. The =comb-cuda-mpi= executable reads existing =comb-*.run= files produced by the CPU/MPI branch. It needs CUDA and MPI; M4RI is optional (=COMB_BUILD_CPU=OFF=). For example:
#+BEGIN_SRC shell
  mpiexec -n 3 build/comb-cuda-mpi comb-example.run
#+END_SRC
Use one MPI rank per GPU. To enable the native multi-GPU tests, configure with =-DCOMB_BUILD_CUDA_MPI_TESTS=ON= and set =COMB_CUDA_MPI_TEST_RANKS= to the allocated rank counts (default =1;2;3=). See =src/mpi/README.md= for Slurm, checkpoint/resume, and options. The original =make -j8= build remains available as a compatibility path.

The complete candidate pipeline now runs in the CUDA kernel: weighted fault unranking, ordered DCP composition, logical variants, CSS X lookup, phase-aware postselection and elimination, and universal Z-coset lookup. GPU threads evaluate independent candidates using disjoint reusable workspaces. Deterministic mode completes the requested interval and returns its smallest bad rank; fast mode may stop early. Native validation on =duvel3= with CUDA 11.8 and three NVIDIA A30 GPUs passes all 24 CTests, including real CUDA/MPI execution with one, two, and three ranks. Synthetic scientific fixtures agree with the independent reference. Production-corpus and performance validation remain open; no speedup is claimed. See =docs/cuda-port-status.md= for the evidence and remaining gates.

For output errors selected in iterator order =E1, E2, ..., Es=, the main CPU implementation folds =E1 * E2 * ... * Es= by right-multiplying each subsequent error into the accumulator. The dependency-free reference and CUDA implementation must preserve that exact order.

Some features of Comb can be set as build time, such as the logging level and a special timing mode that iterates over a given number of fault combinations in order to infer the performance.

In order to set these, one can specify the pertinent macro definitions via the appropriate make invocation as in the following example,
#+BEGIN_SRC shell
  make -j8 CFLAGS='-DTIMING_MODE=1000000 -DLOG_LEVEL=8'
#+END_SRC
* Documentation
[[https://www.doxygen.nl/][Doxygen]] is needed to build the documentation. In order to build it, issue the following
#+BEGIN_SRC shell
  make docs
#+END_SRC
from the project root.

Generated Doxygen output is written to =build/docs=. Tracked design and validation documentation lives in =docs/= and is never removed by =make clean=.
* Future work
There are a variety of improvements to be made which I haven't gotten around to yet. If you are feeling ambitious then try to make a PR!

As always, be aware that performance optimisation can turn out to be not worth it and even make matters worse.

It is unlikely that changes will be merged unless they can demonstrate a benefit and can be seen to preserve correctness of the library.

In order to avoid disappointment, remember to follow standard practices such as benchmarking performance using a profiler, identifying bottlenecks and so forth.

The ideas presented below are not guaranteed to improve performance, they are just what I think is worth looking at.
** Reduce the remaining Gaussian-elimination cost
The main CPU verifier already combines its Z measurements with a precomputed batched transform. The dependency-free reference path retains the earlier sequential measurement sequence so that the two forms can be compared explicitly.

The initial CUDA implementation precomputes stabiliser pivots and measurement sequences in context creation. Each GPU thread performs one candidate's phase-aware elimination sequentially; many candidates run concurrently. Cooperative row operations and a batched-Z GPU transform remain possible optimizations after correctness and profiling on NVIDIA hardware.
** Use Gaussian elimination over finite fields
m4ri has subcubic implementations of Gaussian elimination over $\mathbb{F}_2$ via matrix decomposition.

However, we do not use them. We cannot use such matrix decompositions at present without destroying crucial information about the signs of the Paulis, because the sign bits of the Paulis don't add linearly.

If this could be somehow circumvented, perhaps by using some alternate means to keep track of the signs, we would be able to use more efficient methods of Gaussian elimination.
** SIMD implementation via AVX-512 and/or GFNI
It may be possible to do Gaussian elimination on several stabiliser states at once via SIMD.

Gaussian elimination can be reduced to matrix multiplication (arXiv:1112.5717v2), and matrix multiplication can be done in SIMD via e.g. [[https://www.felixcloutier.com/x86/gf2p8affineqb][GF2P8AFFINEQB]], or VBMACXOR16x16x16.

It's also possible to iterate over $Z$ errors in the coset using Gray codes with SIMD.
** Multithreading
The merged main CPU entry point partitions combinations into chunks and processes them with OpenMP. The MPI layer partitions globally ranked fault combinations across ranks and GPUs, with bounded epochs for deterministic reductions and checkpointing.

Each CUDA worker owns a reusable scratch slice; immutable problem data is replicated per GPU.
